# Contributing

Thanks for helping build a trustworthy PPK2 toolchain. This project values
measurement honesty over feature count: data loss is always surfaced, and
nothing claims to work without evidence.

## Development setup

```bash
git clone https://github.com/tipoLi5890/ppk2lab
cd ppk2lab
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"   # pulls the web extra too, so nothing skips
pytest                # must pass without hardware
ruff check src tests
ruff format --check src tests
mypy
ppk2lab --simulate doctor --json
ppk2lab --simulate web --http-port 0   # the browser console; Ctrl-C exits 0
```

The browser console's sources live in `webui/` (React, TypeScript, Vite) and
its build is **committed** to `src/ppk2lab_web/static/`, so installing from
PyPI never needs a Node toolchain. The cost is that the two can drift, so if
you touch `webui/`, rebuild and commit the bundle in the same change — CI
rebuilds it on every push and fails when the result differs:

```bash
cd webui
npm install
npm run typecheck && npm test && npm run build
git status --porcelain -- ../src/ppk2lab_web/static   # commit what changed
```

## Ground rules

1. **No copied code.** Do not copy, translate, or incorporate source code
   from other projects (including other PPK2 tools). PPK2 behavior is
   referenced from Nordic's official documentation and repository only; see
   `docs/sources.md`.
2. **Self-generated test data.** Every fixture, waveform, and golden capture
   must be produced by this project (`ppk2lab.testing` builders or our own
   hardware fixtures) and documented with its generation method.
3. **Licensing.** New dependencies must be MIT/BSD/Apache-2.0-compatible and
   pass the license scan before merge.
4. **Honest data handling.** Never hide sample gaps, invent defaults for
   unknown values, or silently recover from data loss. If your change can
   drop data, it must emit a `GapEvent`, a warning, or an error annotation.
5. **Hardware safety.** No code path may enable DUT power, change voltage,
   or reset hardware implicitly. State-changing operations report
   requested/before/after state.
6. **Contracts move together.** A change is complete only when code, tests,
   schemas, CLI/API docs, error behavior, and safety implications agree.
   Bumping a schema or capture-format version requires a CHANGELOG entry.

## Tests

- Unit tests must run without hardware (use `MockTransport`/`SimulatedPPK2`).
- Cover framing, partial chunks, counter wrap, gaps, calibration ranges,
  decoder chunk boundaries, and malformed input for anything you touch.
- State-changing hardware tests live apart from unit tests and only run on
  hardware-attached runners.

## Review checklist (applied to every PR)

1. Does the PR copy, translate, or embed code from another project?
2. Is new behavior backed by a spec reference, a test, or a hardware
   observation?
3. Are new fixtures/captures generated by this project, with the method
   recorded?
4. Are dependencies license-compatible and scanned?
5. Do JSON outputs still validate against the schemas, and are error codes
   and exit codes unchanged (or versioned)?

## Commit and PR style

Keep commits focused. In the PR description state the narrow task, how it
was verified (commands + results), and any hardware-safety implications.
