# Protocol research (observation only)

Hard rule: produce observations, specs, and self-generated test vectors —
never implementation code, and never read, copy, translate, or transcribe
source code from other projects. PPK2 behavior references are Nordic
official materials only (`docs/sources.md`).

## Inputs

A specific open question, ideally from `docs/protocol-spec.md`
"Unverified items" (e.g. "does firmware 1.2.4 respond to opcode X?",
"metadata variants on hardware revision Y").

The open questions with the most evidence behind them right now, from the
one hardware session on record — one unit, fingerprint
`HW=49625 IA=59.0 keys=40 ports=2`, macOS:

- **Why does metadata report `Calibrated: 0` on a unit whose five ranges
  all carry constants?** Observed and recorded, not explained. It needs a
  second unit or a second firmware to say whether the flag means anything.
- **How long does VOUT stay energized after the host closes the port?** Off
  in every trial from 500 ms, a coin flip at 100-250 ms, still live at
  0 ms. Established on one unit; whether the threshold is firmware- or
  hardware-determined is open.
- **What is the anchoring offset made of?** A fixed ≈ −2.27 ms independent
  of capture length, with the device clock inside ~10 ppm of the host once
  it is removed. The assumed `ANCHOR_JITTER_S` was deliberately left
  untightened: one unit on one host is not grounds for narrowing a safety
  floor, and narrowing it would weaken a guarantee rather than a guess.

## Workflow

1. Write the hypothesis and the exact observation that would confirm or
   refute it.
2. Observe with read-only paths first: `ppk2lab info --json` (raw metadata
   ships inside captures as `metadata.txt`), `ppk2lab discover --json`
   across replug cycles, OS-level USB descriptors. Record the
   `firmware_fingerprint` (HW, IA, metadata key count, port count) with
   every observation — the measurement port reports no version string, so
   the fingerprint is the only identity an observation can be attributed
   to. It is also in `ppk2lab doctor --json` and every capture manifest.
3. For stream behavior, capture with known stimuli generated by your own
   fixture (`ppk2lab.testing` builders on an MCU, walking-bit patterns);
   keep the `.ppk2a` artifacts as evidence. To look at a long soak
   artifact, `ppk2lab inspect FILE.ppk2a --json` reads its manifest
   without materializing a single sample.
4. Record results:
   - facts → `docs/protocol-spec.md` ("Hardware observations", moving items
     out of "Unverified" with firmware version and date);
   - compatibility outcomes → the matrix in `ROADMAP.md`, keyed on the
     firmware fingerprint the session recorded;
   - test vectors → self-generated, with the generation method written
     down next to them (CLAUDE.md);
   - sources → `docs/sources.md` with access dates.
5. Ambiguous observations stay recorded as ambiguous — never resolved by
   assumption.

Done when each question has: hypothesis, method, evidence artifact,
conclusion (or explicit ambiguity), documentation update — and no
implementation files were modified.
